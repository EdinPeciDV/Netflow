## Day 12: Alert rule management

Added the alert rule CRUD layer that the real-time engine will query in Days 16–25. `AlertRule` entity stores a name, an optional `deviceId` FK (null = applies to all devices), a `metric` enum (`bytes_per_window` / `packets_per_window` / `flow_count_per_window`), a `threshold`, a `windowSeconds` evaluation window (60–86400), an optional protocol filter, and an `enabled` flag. Migration `1793620800000-AlertRules` creates the `alert_rules_metric_enum` type and the `alert_rules` table with a CASCADE FK to `devices` and an index on `deviceId`. `CreateAlertRuleDto` and `UpdateAlertRuleDto` validate all fields via `class-validator` (threshold ≥ 1, windowSeconds 60–86400, protocol 0–255). `AlertRulesService` provides `create`, `findAll`, `findOne`, `update`, and `remove` backed by the TypeORM repository. `AlertRulesController` is class-level JWT-guarded — `GET /alert-rules` and `GET /alert-rules/:id` are open to any authenticated user; `POST`, `PATCH :id`, and `DELETE :id` are additionally guarded by `RolesGuard` and require the admin role. `AlertRulesModule` exports the service so the future `AlertsModule` can inject it without re-importing the entity. Wired into `AppModule`.

## Day 13: Flow time-series aggregation

Added a time-bucketed aggregation endpoint on top of the existing flow data. `AggregateFlowsDto` accepts an optional `deviceId` (UUID filter), a `bucket` enum (`hour` / `day` / `week`, default `hour`), and optional ISO-8601 `startFrom` / `endBefore` bounds. `FlowsService.aggregate` builds a `date_trunc`-based `QueryBuilder` that groups rows by the chosen bucket and returns `flowCount`, `totalBytes`, and `totalPackets` per bucket ordered ascending — ready to feed straight into a time-series chart. `FlowsController` exposes the new `GET /flows/aggregate` route under the existing class-level `JwtAuthGuard`.

## Day 14: Alert events

Added the `AlertEvent` entity so the system can persist when a threshold is breached. The entity stores `alertRuleId` (FK → `alert_rules` CASCADE), an optional `deviceId` (FK → `devices` SET NULL), the `metric` enum, the numeric `value` that triggered the event, and a `triggeredAt` timestamp — all three FKs are individually indexed. Migration `1793707200000-AlertEvents` creates the `alert_events` table reusing the existing `alert_rules_metric_enum` type. `AlertEventsService` exposes `create`, `findAll` (filterable by `alertRuleId` and `deviceId`, paginated by `limit`), and `findOne` with a 404 guard. `AlertEventsController` wires `GET /alert-events` and `GET /alert-events/:id` behind `JwtAuthGuard`. `AlertEventsModule` exports the service so the future evaluation scheduler can inject it without reimporting the entity. Wired into `AppModule`.

## Day 15: Alert threshold evaluation

Completed the backend core phase by wiring the alert rule evaluation loop. Added `EvaluateAlertDto` (`deviceId` UUID, `metric` enum, `value` number ≥ 0) backed by `class-validator` so the global `ValidationPipe` enforces the shape at the boundary. `AlertEventsService.evaluate` queries all enabled alert rules that match the given metric and device (or are device-global with `deviceId IS NULL`), compares the measured value against each rule's threshold, and fires an `AlertEvent` row for every breach. The evaluation is intentionally synchronous — the ingestion path will call it inline in Day 16 when the WebSocket layer lands. `AlertEventsModule` now also registers `AlertRule` via `TypeOrmModule.forFeature` so the service can query rules without crossing module boundaries. `AlertEventsController` gains a `POST /alert-events/evaluate` endpoint guarded by `JwtAuthGuard` — the ingestion worker will call it internally, but it is also testable via HTTP during development. Backend core phase complete.

## Day 16: WebSocket gateway for real-time flow events

Kicked off the real-time layer by adding a Socket.io WebSocket gateway to the backend. Installed `@nestjs/websockets`, `@nestjs/platform-socket.io`, and `socket.io`. Created `FlowsGateway` — a `@WebSocketGateway` on the `/flows` namespace with CORS open — that holds a reference to the Socket.io `Server` and exposes a `broadcastFlows(records)` method. Implemented `OnGatewayConnection` and `OnGatewayDisconnect` to log client connect/disconnect events for visibility during development. `FlowsGateway` is registered as a provider in `FlowsModule`. `FlowsService` now injects the gateway; at the end of `ingest`, after all `FlowRecord` rows are persisted, it calls `gateway.broadcastFlows(records)` to push the new records to every connected WebSocket client as a `flows:new` event. Frontend clients can subscribe to `ws://<host>/flows` and receive live flow data the moment a device posts to `POST /flows/ingest`.

## Day 18: Redis caching for alert-rule evaluation

Added Redis caching to the alert evaluation hot-path so a DB query is no longer issued for every metric checked on every ingest batch. `AlertEventsService.evaluate` now reads enabled rules for the requested metric from a Redis key (`alert-rules:<metric>`) with a 30-second TTL; on a miss it queries PostgreSQL and populates the cache. Device-specific filtering is performed in memory against the cached list, keeping the cache granularity at the metric level and making the cache useful across all devices. `AlertRulesService` injects `CACHE_MANAGER` and calls `invalidateRulesCache()` after every `create`, `update`, and `remove` mutation, deleting all three metric keys so stale rules are never evaluated. `CacheModule.registerAsync` is registered globally in `AppModule` using `cache-manager-ioredis-yet`'s `redisStore`, configured from `redis.host` / `redis.port` via `ConfigService` with a default TTL of 30 seconds. Packages added: `@nestjs/cache-manager`, `cache-manager`, `cache-manager-ioredis-yet`, `ioredis`.

## Day 17: Auto-evaluate alert thresholds on ingest + AlertsGateway

Closed the loop between the ingestion pipeline and the alert engine. Added `AlertsGateway` — a `@WebSocketGateway` on the `/alerts` namespace — that exposes `broadcastAlert(event)` emitting `alerts:triggered` to all connected clients. `AlertsGateway` is registered in `AlertEventsModule` alongside `AlertEventsService` and exported from both so other modules can inject it. `FlowsModule` now imports `AlertEventsModule`, giving `FlowsService` access to both `AlertEventsService` and `AlertsGateway` without redeclaring their entities. At the tail of `FlowsService.ingest`, after rows are persisted and flow records are broadcast, the service computes per-batch totals (sum of bytes, sum of packets, flow count) and fires `AlertEventsService.evaluate` for each of the three `AlertMetric` values against the ingesting device. Any rules whose thresholds are breached produce `AlertEvent` rows in the database; each fired event is immediately pushed over the `/alerts` WebSocket namespace as `alerts:triggered`. Clients subscribed to `/alerts` now receive threshold breaches in real time the instant an offending flow batch lands.

## Day 19: Alert cooldown / deduplication

Stopped the alert engine from storming. Because `FlowsService.ingest` calls `AlertEventsService.evaluate` on every batch, a device that stays above a threshold used to mint a fresh `AlertEvent` row and fire an `alerts:triggered` WebSocket broadcast for *every* ingest — potentially many per second. Added a per-rule cooldown so a breached rule fires at most once per cooldown window for a given device. `AlertRule` gains a `cooldownSeconds` column (`int`, default 300 = 5 min); migration `1793793600000-AlertRuleCooldown` adds it via `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT 300`. `CreateAlertRuleDto` and `UpdateAlertRuleDto` validate it with `@IsInt() @Min(0) @Max(86400)` (0 disables the cooldown entirely). In `evaluate`, once a rule's threshold is breached the service checks a Redis key `alert-cooldown:<ruleId>:<deviceId>`; if present the breach is suppressed, otherwise it fires the `AlertEvent` and sets the key with a TTL of `cooldownSeconds * 1000` ms (reusing the Day 18 cache-manager/ioredis store). Keying on the concrete `deviceId` keeps per-device isolation for device-global rules (`deviceId IS NULL`) — device A going quiet-period never masks device B breaching the same rule. The cooldown state lives only in Redis, so it survives app restarts without touching PostgreSQL and expires on its own.

## Day 20: JWT authentication for WebSocket gateways

Closed an auth gap in the real-time layer: the REST routes were all JWT-guarded, but anyone could open a Socket.io connection to `/flows` or `/alerts` and receive live traffic data and alert events. Added `WsAuthService` to `AuthModule` (exported alongside `JwtAuthGuard`). It pulls the token from `handshake.auth.token` first — browsers can't set an `Authorization` header on a WebSocket handshake, so socket.io's `auth` option is the primary path — and falls back to a standard `Authorization: Bearer` header for non-browser clients, stripping an optional `Bearer ` prefix. It verifies the signature and expiry with `JwtService.verifyAsync`, then re-loads the user via `UsersService.findById` so a deleted account's still-valid token is rejected, returning `null` on any failure. `FlowsGateway` and `AlertsGateway` now inject it and run it in `handleConnection`: unauthenticated clients get an `error` event (`{ message: 'Unauthorized' }`) and are disconnected immediately; authenticated clients have the user attached to `client.data.user` for later per-user logic. `FlowsModule` and `AlertEventsModule` import `AuthModule` to get the service. Added `ws-auth.service.spec.ts` (6 tests covering both token sources, the Bearer prefix, missing token, bad token, and missing user) — the spec stubs `@nestjs/jwt` because its ESM build can't be parsed by Jest's CJS runtime. Frontend clients will connect with `io('/flows', { auth: { token } })`.

## Day 21: Per-device room subscriptions on the /flows gateway

Until now every authenticated `/flows` client received every `flows:new` broadcast for every device, which doesn't scale once a dashboard only cares about a few devices. `FlowsGateway` now uses Socket.io rooms: on connect each client joins `flows:all` (so existing clients behave exactly as before). Sending `flows:subscribe` with `{ deviceIds: [...] }` makes the client leave `flows:all` and join one `flows:device:<id>` room per device (input is filtered to strings and capped at 50 per request; an empty list is a no-op), acking with the subscribed ids. `flows:unsubscribe` drops all device rooms and rejoins `flows:all`. `broadcastFlows(deviceId, records)` now emits to `[flows:all, flows:device:<id>]` in one call — Socket.io de-duplicates across rooms, so a client never receives the same batch twice — and `FlowsService.ingest` passes `dto.deviceId`. Added `flows.gateway.spec.ts` (5 tests: subscribe, invalid/empty subscribe, cap, unsubscribe, broadcast targeting), stubbing `@nestjs/websockets` and `@nestjs/jwt` for the same ESM-in-Jest reason as Day 20.

## Day 22: Rate limit on flows:subscribe

`flows:subscribe` makes the server leave and join rooms, so a misbehaving or buggy client hammering it (e.g. a UI re-subscribing in a render loop) could churn rooms indefinitely. `FlowsGateway` now applies a per-socket sliding-window limiter: at most 10 `flows:subscribe` calls per 10 s (`SUBSCRIBE_LIMIT` / `SUBSCRIBE_WINDOW_MS`). Call timestamps live in `client.data.subscribeHits`, so state is per connection and disappears on disconnect — no Redis involved. Over the limit the handler skips all room changes and acks `{ error: 'rate_limited', retryAfterMs }`, where `retryAfterMs` is the time until the oldest call leaves the window, so clients can back off precisely. `flows:unsubscribe` is not limited. Added 3 tests to `flows.gateway.spec.ts` (11th call rejected, allowed again after the window, limits tracked per client) by stubbing `Date.now`; 8 tests total in the spec.

## Day 24: Per-device alert subscriptions on /alerts gateway

Mirrored the `/flows` room-subscription model on the `/alerts` gateway so dashboard clients stop receiving every alert for every device. On connect each client joins `alerts:all` (backwards-compatible). Sending `alerts:subscribe` with `{ deviceIds: [...] }` leaves the all-room and joins one `alerts:device:<id>` room per device (input filtered to strings, capped at 50 per request; empty list is a no-op); `alerts:unsubscribe` drops all device rooms and rejoins `alerts:all`. `broadcastAlert` now targets `[alerts:all, alerts:device:<deviceId>]` — when the event has no `deviceId` it only targets `alerts:all`, and Socket.io de-duplicates across rooms. Added the same per-socket sliding-window rate limiter from `/flows`: at most 10 `alerts:subscribe` calls per 10 s, ack `{ error: 'rate_limited', retryAfterMs }` when over. Created `alerts.gateway.spec.ts` (9 tests: subscribe, empty/invalid subscribe, cap 50, unsubscribe, broadcast with device, broadcast without device, rate limit reject, rate limit window reset, per-client isolation).

## Day 23: Server-side heartbeat for the /flows gateway

Socket.io's transport-level ping/pong detects hard network cuts, but application-layer zombies — connections where the client process is alive but stuck, or the browser tab is frozen — stay invisible to the server indefinitely. `FlowsGateway` now runs its own heartbeat: after `handleConnection` succeeds, `scheduleHeartbeat` sets a 30 s timer (`HEARTBEAT_INTERVAL_MS`); when it fires the gateway emits `gateway:ping` to the client and starts a 5 s pong-wait timer (`PONG_TIMEOUT_MS`). A `gateway:pong` message from the client sets `client.data.pongReceived = true` and reschedules the next heartbeat; if the pong timer fires and `pongReceived` is still false, the client is forcibly disconnected. All timers are stored in `client.data` and cleared in `handleDisconnect`, so there are no leaks. The heartbeat is per-connection and stateless beyond the two timeout handles — no Redis, no server-wide state.
